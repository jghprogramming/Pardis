# مدیریت شارژ ساختمان — ساختار پروژه واقعی

این پوشه، اسکلت پروژه واقعی محصول اشتراکی مدیریت شارژ ساختمان است؛ نه نسخه نهایی کامل.
هدفش این است که توسعه بعدی راحت، نسخه‌دار و قابل انتشار باشد.

## محصول در یک نگاه

- محصول اشتراکی و چندساختمانی، با تعداد نامحدود ساختمان و واحد
- سه نقش: مدیر محصول، مدیر ساختمان و ساکن
- همه روش‌های محاسبه شارژ: ثابت، بر اساس متراژ، بر اساس تعداد نفر و ترکیبی، به‌همراه هزینه‌های خاص هر دوره
- پرداخت آنلاین ساکنان و پرداخت اشتراک ساختمان‌ها از طریق زرین‌پال
- دوره‌های اشتراک: ماهانه، ۳ ماهه، ۶ ماهه و سالانه؛ سالانه با ۱۰٪ تخفیف
  - مثال: اگر قیمت ماهانه یک پلن P باشد، قیمت سالانه آن ۱۰٫۸ برابر P است
- فعلاً فقط ساختار پلن‌ها تعریف می‌شود، نه قیمت نهایی واقعی
- رابط فارسی، کاملاً راست‌چین، فونت وزیرمتن، تقویم شمسی (جلالی) و اعداد فارسی
- تم سبز و خاکستری، وب‌اپ PWA و موبایل‌محور

## پشته فناوری

- فرانت‌اند و بک‌اند: Next.js با TypeScript و React
- پایگاه داده، احراز هویت و ذخیره‌سازی: Supabase با PostgreSQL
- میزبانی و انتشار خودکار: Vercel
- کنترل نسخه: Git و GitHub
- پرداخت: زرین‌پال (در نمونه فعلی فقط نمایشی است؛ اتصال واقعی در مرحله استقرار لازم است)
- پیامک یادآوری: در مرحله بعد، با سرویسی مثل کاوه‌نگار

## جدول‌های اصلی پایگاه داده

فایل کامل در `supabase/migrations/001_init.sql` است. جدول‌های اصلی:

- `profiles`: کاربر و نقش او؛ مدیر محصول، مدیر ساختمان یا ساکن
- `plans`: نام پلن، قیمت پایه ماهانه، سقف تعداد واحد، امکانات و وضعیت فعال
- `buildings`: ساختمان، مدیر آن و پلن فعالش
- `subscriptions`: اشتراک هر ساختمان، دوره آن، تاریخ شروع و پایان و وضعیت
- `subscription_invoices`: صورت‌حساب اشتراک ساختمان‌ها
- `units`: واحد، متراژ، تعداد ساکن، مالک یا مستأجر
- `charge_periods`: دوره شارژ ماهانه، روش محاسبه و هزینه خاص دوره
- `bills`: صورت‌حساب هر واحد، مبلغ پایه، سهم هزینه خاص، جریمه و مانده
- `payments`: پرداخت‌ها، روش پرداخت و کد پیگیری
- `expenses`: هزینه‌های ساختمان و صندوق

دسترسی‌ها باید با Row Level Security در Supabase محدود شود: مدیر محصول همه ساختمان‌ها را می‌بیند،
مدیر ساختمان فقط ساختمان خودش را، و ساکن فقط صورت‌حساب واحد خودش را.

## متغیرهای محیطی

از روی `.env.example` یک فایل `.env.local` بسازید و مقدارهای واقعی را همان‌جا بگذارید.
مقدارهای واقعی، رمز و کلید را هرگز داخل کد یا چت نگذارید.

- `NEXT_PUBLIC_SUPABASE_URL` و `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`
- `ZARINPAL_MERCHANT_ID`
- `NEXT_PUBLIC_APP_URL`

## چرخه توسعه و انتشار

1. هر تغییر در یک شاخه جدا در Git ساخته می‌شود.
2. Vercel برای همان تغییر یک نسخه پیش‌نمایش می‌سازد تا بررسی شود.
3. پس از تأیید، تغییر به شاخه اصلی می‌رود و نسخه اصلی به‌صورت خودکار منتشر می‌شود.
4. تغییر ساختار پایگاه داده فقط با Migration انجام می‌شود تا داده ساختمان‌ها و صورت‌حساب‌ها پاک نشود.
5. اگر تغییری مشکل ساخت، انتشار قبلی در Vercel بازگردانده می‌شود.

## مرحله‌های بعدی، به ترتیب

1. ساخت مخزن GitHub و اتصال آن به Vercel
2. ساخت پروژه Supabase و اجرای `supabase/migrations/001_init.sql`
3. پیاده‌سازی ورود و نقش‌ها، سپس ماژول پلن و اشتراک
4. پیاده‌سازی واحد، دوره شارژ و صورت‌حساب
5. اتصال واقعی زرین‌پال در محیط آزمایشی، سپس محیط اصلی
6. اتصال پیامک یادآوری و انتشار نسخه اصلی

## وضعیت فعلی

- اسکلت، ساختار پوشه‌ها، پیکربندی پایه و طرح پایگاه داده آماده است.
- ورود و نقش‌ها (`src/lib/auth.ts`، صفحه `/login`) و ماژول پلن‌های مدیر محصول
  (صفحه `/plans`) هم به‌صورت کد نوشته شده است؛ ولی هنوز با پایگاه داده واقعی
  تست نشده است، چون پروژه Supabase هنوز ساخته نشده است.
- بقیه ماژول‌ها، اتصال واقعی زرین‌پال و پیامک هنوز پیاده نشده است و در مرحله‌های بعدی،
  ماژول‌به‌ماژول ساخته می‌شود.
